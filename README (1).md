# Dialogflow ES latency study: code, data and agents

Replication package for **"Performance Characterization of Dialogflow ES as Conversational Middleware: End-to-End Latency, Stage Decomposition, and Load Behaviour"** (E. Modiridovom, R. Mundlamuri, D. Akopian, P. Chalela; manuscript SNCS-D-26-05361, under review at *SN Computer Science*).

The study measures how much latency a Dialogflow ES webhook-fulfillment path adds compared with calling the same external API directly, how that overhead splits between Dialogflow, the tunnel and the webhook, and how it behaves under burst and sustained load, in four domains: Weather, Capital City, Currency and Joke.

Every table, figure and number in the paper is generated by one script (`analysis/analysis.py`) from the raw logs in `data/raw/`. Running `scripts/reproduce_analysis.sh` rebuilds them all.

## Repository layout

```
harness/bench_harness.py      measurement harness: instrumented webhook, four configurations, experiments, logging
analysis/analysis.py          builds all tables, figures and numbers.json from the raw logs
notebooks/run_experiments.ipynb   Google Colab notebook to re-run the experiments
scripts/reproduce_analysis.sh     rebuilds results/ from data/raw/
scripts/supplementary_analysis.py numbers reported only in the text (time to eventual success, quota timing, transient failures)
data/queries.json             test queries per domain (79 weather, 80 capital, 60 currency, 5 joke)
data/raw/                     raw logs of the three measurement sessions reported in the paper
data/preliminary/             one preliminary run, not used in the paper (see below)
data/currency_extraction/     Currency entity-extraction checks before and after the agent correction
agents/                       Dialogflow ES agent exports (see agents/README.md)
results/                      tables (CSV and LaTeX), figures and numbers.json, as reported in the paper
```

## Reproduce the paper's results (no Google account needed)

```bash
pip install -r requirements.txt
bash scripts/reproduce_analysis.sh
```

## Raw log format

**`attempts.csv`**: one row per request attempt (retries are separate rows).

| Column | Meaning |
|---|---|
| `run_id` | session identifier |
| `experiment`, `phase` | `sequential`, `burst`, `sustained` or `warmup`; `phase` is `measure` or `warmup` (warm-up rows are excluded) |
| `domain`, `arch` | domain; configuration `A` (Dialogflow), `C` (tunnel + webhook control), `L` (local webhook control), `B` (direct API) |
| `request_uid`, `attempt` | one logical request; attempt number (1 = first attempt) |
| `block`, `batch_size`, `rate_rps`, `order_index` | sequential block or burst run; burst size; offered rate (sustained); position in randomised order |
| `query_label`, `query_text` | ground-truth label and query text |
| `ts_utc_start`, `t_sched_s`, `t_send_s` | start time; scheduled and actual send time in the sustained test |
| `latency_ms` | client-measured latency of the attempt |
| `transport_ok`, `intent_ok`, `webhook_ok`, `api_ok`, `success_e2e` | stage outcomes; `success_e2e` requires all four |
| `error_class`, `error_detail`, `status_code` | failure class (`nlu_intent`, `nlu_entity`, `webhook`, `api`, `quota`, `timeout`, `transport`, `df_error`) and details |
| `matched_intent`, `intent_confidence` | Dialogflow's matched intent and confidence (A only) |
| `extracted_entity`, `expected_entity`, `entity_match` | extracted vs ground-truth entity |
| `wh_handler_ms`, `wh_api_ms`, `wh_parse_ms`, `api_http_status` | timings and API status reported by the webhook (A, C, L) |

**`webhook_log.csv`**: one row per webhook call, server side, including the raw parameters received.

**`run_metadata_<run_id>.json`**: environment (VM location, CPU, memory, Python and package versions) and every harness setting.

## Currency agent correction

`data/currency_extraction/currency_extraction_original_agent.csv` shows that the original Currency agent extracted the correct currency pair for 0 of the 60 test queries. `currency_extraction_corrected_agent.csv` shows 60 of 60 after the correction. The reported Currency results use the corrected agent. `agents/README.md` documents the original configuration.

## Preliminary run (not used in the paper)

`data/preliminary/2026-11-04_preliminary_run/` holds a preliminary run made before three harness settings were corrected: the webhook thread pool, a fixed ngrok region and unequal HTTP connection reuse between configurations. It is included for transparency and is not used in any reported result. The Currency extraction check made during that session is in `data/currency_extraction/currency_extraction_original_agent.csv`.

## Re-running the experiments

1. Restore the four agents from `agents/` into your own Google Cloud projects, and create a service-account key for each.
2. Open `notebooks/run_experiments.ipynb` in Google Colab and follow the cells: configure, start the webhook, paste the printed URLs into the agents, run the preflight, then run each domain.
3. Analyse your logs with `analysis/analysis.py`.

Absolute latencies depend on the client's location and network, the Dialogflow edition and the external APIs, so expect different values. The design (paired comparisons, controls, stage timing) is what transfers.

## Redactions

The logs, metadata and agent exports contain no credentials. Tunnel host names were replaced with `REDACTED-TUNNEL-HOST` or `YOUR-TUNNEL-HOST`. The harness reads all credentials from environment variables.
